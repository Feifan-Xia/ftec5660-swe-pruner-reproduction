## 1. 复现目标与范围

SWE-Pruner 用于减少编程 Agent 从工具中接收的代码上下文。其发布的小模型根据当前关注问题（focus query）对代码 tokens 评分，保留相关片段，让 Agent 继续进行多步仓库调查。本项目使用作者的 OpenHands 评测流程 [2]，复现论文表 2 中 SWE-QA 的 Streamlink 子任务 [1]，重点测量回答质量与累计 LLM 输入、输出 tokens 之间的关系。

实验从作者提供的 48 道 Streamlink 问题中选取固定子集，对比完整工具输出、作者的可选关注问题剪枝，以及增加原文精确恢复工具后的剪枝。可恢复观测接口是本项目的单一主要修改。项目还直接验证发布权重的剪枝行为，并记录在 8 GB 笔记本 GPU 上运行所需的适配。

本地 Agent 使用 OpenCode Go 提供的 DeepSeek V4.1 Flash。论文使用 Claude Sonnet 4.5 和 GLM-4.6，因此论文数字用于提供背景，本地三组配对实验用于评估本次修改。基础模型、样本规模、推理后端和运行上限的差异，都需要纳入结果解释。

## 2. 环境与复现控制

作者仓库固定为 commit 96171b5f3ecaf89745cbeb436c8893b57f3400bd，Streamlink 固定为 ab1f3656。问题 JSONL 的 SHA-256 为 af5d149b7a256b85d50c0d5971f42c3504f14f97632708bb06c1d486c6db0162。选题种子为 5660，开发题索引为 43、26、17，与正式题分开。正式题为 41、14、30、8、11、46、33、29。回答 Agent 的输入文件仅包含问题文本，参考答案用于评分。

Bash 工具保留本地文件系统权限。审计逐条检查已记录命令是否直接引用已知的问题、答案和实验产物路径，并核对输入文件与原始问题文本一致。含父目录跳转的命令经过单独路径核查，保留精确命令及理由。该审计的证据范围是输入构造与已观察到的访问行为，文件系统访问权限仍由本地环境提供。

硬件为 NVIDIA RTX 5060 Laptop，显存 8,151 MiB，驱动版本 591.59。Windows 剪枝服务复用现有 PyTorch 2.9.0.dev20250705+cu129、Transformers 4.57.1，以及 ayanami-kitasan/code-pruner 发布权重，权重文件大小为 1,345,834,856 字节。Agent 在 WSL Ubuntu 22.04、Python 3.12、OpenHands SDK 1.1.0 环境运行；通过镜像 localhost 网络连接剪枝服务和 API 预算代理。

作者的 Bash 执行器为每条命令设置 10 秒超时。Agent 可能从工具超时中恢复并继续作答，因此工具超时与整题失败分别统计。Streamlink 使用 blob filtering 克隆，部分历史对象可能需要按需下载；本地缓存及网络状态会影响历史对象可用性和耗时比较。

API 地址为 https://opencode.ai/inference/go/openai/v1，密钥存放在本地被 Git 忽略的环境文件中。正式请求记录的实际参数为 temperature=0.0、top_p=1.0、每次最多输出 4,096 tokens；SDK 配置未显式填写 temperature，以发出的请求为准。作者的兜底回答请求使用 temperature=0.3。三组统一采用 30 轮 Agent 上限、每题 600 秒上限和 0.4 剪枝阈值。三次重复用于观察这些设置下由模型服务和工具行为共同产生的运行波动。

为适应笔记本显存，推理采用 SDPA，省略未使用的 attention weights，并去掉单样本输入中被 mask 的右侧 padding。权重以 BF16 存储，保留作者的 FP16 autocast。两组固定探针对比了 attention weights 计算与 padding 设置，包括补齐到 8,192 个位置的情况。所有 tokens 在 0.4 阈值下的保留决策一致，最大概率差为 0.01653。这项敏感性检查支持已测试样例；更广泛的数值一致性仍需验证。

## 3. 实验条件、指标与分析方法

baseline 使用作者的完整输出 Bash 工具。pruner 暴露作者的 context_focus_question 参数，Agent 提供该参数时才触发剪枝。因此，实验同时统计分配到剪枝组的任务数和真正发生剪枝的次数。

recovery 保留相同剪枝机制，并增加观测 ID、原始行数和 expand 工具。存储器保存原始字符串，使用从 1 开始、两端均包含的行范围进行恢复，每次最多返回 200 行；记录读取次数与重复读取行数。每个任务拥有独立存储器，避免任务间共享观测。

30 轮上限针对 Agent 的轮次，一轮可包含多个工具动作，因此工具观测数可以超过 30。达到上限后还可能发起额外的兜底回答请求。资源消耗与机制调用次数均从实际记录统计。

正式实验采用 8 道题 × 3 组 × 3 次重复，共 72 次尝试。各组顺序随题目及重复轮次轮换，以分散时间漂移影响。全部计划尝试均保留；完成率包含失败，资源统计包含归属于该次尝试的全部 API 请求。回答均分以有效导出并完成评分的答案为分母，另提供将失败记为 0 分的敏感性分析。作者原有的分数过滤口径作为辅助统计保留。

评分沿用官方 rubric：正确性、完整性、相关性、清晰度和推理质量，每项为 1–10 的整数，任务得分为五项均值。Judge 使用官方提示词、temperature=0，以及与回答 Agent 相同的 DeepSeek 模型。各组评分方式保持一致；同模型评分偏差、小样本规模及缺少独立人工评分限制了结论的推广范围。

初始评分请求最多输出 2,048 tokens，部分响应在生成完整 JSON 前耗尽额度。对缺失或无效评分，最多执行两次 4,096-token 补评分，rubric、模型和 temperature 保持一致；保留初始响应及额外用量，已有有效评分保持原值。最终共有 3 份评分完成补充，所有有效导出答案均已评分。

累计 tokens 采用服务商逐请求 usage，评分调用通过 session ID 单独区分。输入包含缓存命中的 prompt tokens，输出包含服务商报告的 reasoning tokens。现金收费、Go 额度消耗、服务商 list cost 与按未缓存峰值价格计算的保守预算分别列示。

整题耗时根据原始 task.json 与 exit.json 的写入时间重建一次，并保存为独立计时文件；包含进程启动、工具执行、API 等待和清理，覆盖失败尝试，评分时间单独排除。作者原有的有效答案耗时另行保留。重复轮次的均值与标准差描述运行波动；配对比较先在每道题内平均三次重复，再在题目层面比较各组。

### 4.1 轨迹核查：未触发剪枝时的差异

第 41 题、repeat 0 中，三组均定位到 TestIO.test_load_data 及其 cache._dirty 断言，与参考答案的核心位置一致，评分均为 10.0。baseline、pruner、recovery 的累计 tokens 分别为 36,663、46,492、36,787。三条轨迹均未触发剪枝或恢复。

这一案例展示了仓库问答能力与轨迹间波动。解释 token 差异时，需要考虑工具可用性与后续动作序列；该案例没有提供“压缩导致差异”的直接证据。案例说明与原始证据一起保存，核查由 AI 辅助完成，独立人工评价仍有待开展。

### 4.2 自主恢复与组件演示

第 41 题、repeat 1 出现了正式的自主恢复：一段 29 行的仓库搜索结果从 851 个源 tokens 剪到 6 个，只剩过滤行数提示。Agent 随即调用 expand 恢复全部 29 行，取回精确原文及 TestIO 文件位置，随后定位目标测试与断言，评分为 10.0。

该次 recovery 累计消耗 101,923 个 API tokens，同题同轮 baseline 和 pruner 分别为 53,433、29,340。轨迹证明恢复入口被 Agent 自主使用，并记录了整题资源消耗。若要把质量改善归因于某一次恢复调用，还需要固定轨迹的受控回放。

组件 demo 使用 217 行的 albavision.py，以及关于 token 转换和相邻小时时间戳的问题。发布模型将 1,687 个代码 tokens 压缩到 169 个，保留转换函数及当前、前一小时的调用，观测请求约两秒完成。另一次真实代码服务检查测得峰值已分配显存约 2.88 GB。

demo 随后通过观测 ID 取回第 191–215 行，并验证返回字符串与保存的原始范围完全一致。该组件演示由脚本选择恢复范围，Agent 自主恢复能力另由正式轨迹测量。单元测试还覆盖 CRLF/LF 混合换行、Unicode、重叠读取、未知 ID、无效范围和单次行数上限。

## 5. 调试记录与实现调整

最初在 WSL 中安装完整 GPU 依赖时触发了较大下载。检查本机后发现已有可用 CUDA PyTorch 环境，最终通过隔离环境复用，完成 GPU 部署。大文件下载结合文件大小与网络路由选择安排。

原 runner 无条件启用 Claude 专用 HTTP patch，在 OpenAI-compatible 接口上尚未有效运行便报错。关闭该 patch 后客户端恢复运行。本地服务调用显式绕过环境代理；外部 TLS 建连失败则定位到显式代理配置，并通过调整客户端解决。逐请求账本保留完成用量与传输错误。

初始预算守门在 TLS 建连失败时仍保留请求额度。ConnectError 发生在请求发送前，其临时预留被释放，原账本行继续保留；发送后结果不明确的请求继续保留保守预留，从而区分已知未发出和结果不确定的情况。

作者原有统计同时累加累计计数器及其分项，导致 token 重复计数；将对应分支改为 elif 后消除重复，本项目以服务商逐请求 usage 为统计依据。另为可选 usage_id 增加默认值，并调整配置输出以保护密钥。这些兼容性和计费修复作用于相关条件；主要实验干预仍为可恢复观测接口。

正式 recovery 第 14 题、repeat 0 达到 30 轮上限后，暴露了兜底路由问题：直接 OpenAI 客户端向服务商传递 SDK 使用的 openai/ 模型前缀，同时遗漏任务 session header。该次尝试保留为失败。前 6 次计划尝试之后，修复为规范模型名与现有任务 headers，并归档 V1、V2 源码；使用记录请求的客户端桩测试验证。模型、提示词、运行上限、阈值与 Judge 保持一致。中途基础设施修复及保留的失败需要纳入合并结果的因果解释。

初始 FP32 模型配合固定 8,192 长度 padding 时显存压力较大，并超过服务超时。明确权重存储精度、使用单样本动态长度、去掉未使用的注意力矩阵后，推理显存占用降低。数值探针及环境记录保留了这些实现差异的验证范围。

baseline 第 33 题、repeat 1 的轨迹中包含完整 FinishAction.message，但导出答案为空。作者提取器检查 action.name，而该 SDK 动作的 name 为 null，以 kind=FinishAction 标识类型；该轨迹仅有 8 个动作，也未触发兜底请求。主统计保留导出失败与资源消耗。因此，本报告的完成率衡量有效答案的导出可用性；轨迹另行记录模型已经生成回答这一事实。正式运行配置和原始评分均保留。

pruner 第 11 题、repeat 2 达到轮次上限后，成功调用修复后的兜底路由，但服务商报告全部 4,096 个 completion tokens 都用于推理，最终答案为空。该次受限生成失败保留在主统计中，相关 tokens 与费用全部计入。

## 6. 结论与限制

72 次正式尝试全部执行，三组各导出 23/24 份有效答案。平均累计 API tokens 分别为 125,036、183,425、140,734；pruner 比 baseline 高 46.7%，recovery 比 pruner 低 23.3%，比 baseline 高 12.6%。有效答案均分分别为 9.87、9.74、9.83；失败记零后的均分为 9.46、9.33、9.42。两组配对 token 差异的 bootstrap 区间及失败记零评分区间均跨零，8 道题提供的估计精度有限。

发布模型的剪枝机制实际运行：pruner 组共剪枝 119 次，保留对应源 tokens 的 53.1%；recovery 组剪枝 68 次，在两道题中自主调用 expand 共 3 次，重复读取行数为零。实验验证了工具输出压缩和精确恢复能力；本次本地评测未复现论文总体 token 节省的方向。可选剪枝是否激活、Agent 调查轨迹以及新增恢复接口都会影响后续行为，因此单次输出压缩比例需要与端到端累计用量一起解释。

三类失败分别来自兜底路由、答案导出和推理额度耗尽。基础模型差异、同模型 Judge、小子集及中途基础设施调整共同限制了因果推断与总体推广。项目形成了固定版本的可运行流程、原始证据和可复用观测接口；后续可通过更大规模独立评测与受控恢复回放检验收益。

面向 XJ13 的可复用部分是任务级观测存储器，提供稳定 ID、精确行恢复和读取统计，也可通过字符串接口接收序列化 JSON。XJ13 的 lookup、conditional、aggregation 任务需要单独评估，本报告测量的是编程 Agent 场景。

后续复现应同时记录实际剪枝次数、缓存相关用量和失败类型，固定仓库与问题版本，使用有代表性的工具输出检查显存，并将开发调试与正式计划运行分开保存。这些控制有助于在可访问模型与论文模型不同时解释实际取舍。
